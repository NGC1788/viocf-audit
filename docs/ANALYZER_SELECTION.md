# 분석기 선택 근거

기준일: 2026-08-27 · 재현: `scripts/benchmark_f0_backends.py`, `scripts/benchmark_surrogate.py`

이 문서는 "왜 2002년 알고리즘을 쓰는가"에 답한다. **답은 최신을 실제로 재봤더니 졌기 때문이다.**

## 왜 흔한 벤치마크로는 고를 수 없나

피치 추정 논문의 표준 지표는 RPA/RCA — "정답의 50 cents 안에 들어왔나"를 센다.
그 기준으로는 아래 5개가 전부 99% 를 넘고 우열이 안 갈린다.

하지만 이 연구의 headline 은 **"강약을 바꿨더니 음정이 N cents 움직였다"** 이다.
필요한 건 절대 정확도가 아니라 **같은 음 안에서 조건 간 '차이'의 정확도**다.
절대 편향은 같은 음끼리 비교하면 상쇄되지만, 차분 오차는 그대로
**가짜 누출** 또는 **놓친 누출**이 된다. 그래서 그 양으로 직접 겨뤘다.

## (A) 차분 정확도 — 결정적 기준

합성 정현파(배음 16개, 2.5 s), 3 음역, 주입 오프셋 7 / 23 / 47 cents.

| 추정기 | 공개 | 평균 차분 오차 |
|---|---|---|
| **librosa `yin`** | 2002 | **0.29 cents** |
| librosa `pyin` (resolution=0.05) | 2014 | 2.33 cents |
| CREPE full (torchcrepe) | 2018 | 5.44 cents |
| PESTO | 2023/2025 | 12.29 cents |
| SwiftF0 0.1.2 | 2025 | 141.29 cents (G5 에서 옥타브 오류) |

> ⚠ **주입값을 10/25/50 처럼 둥근 수로 잡으면 안 된다.** 격자형 추정기가 우연히
> 맞아떨어져 pyin 이 0.00 cents 로 보인다(실제로 처음에 그렇게 나왔다).
> 격자와 서로소인 7/23/47 로 재야 진짜가 드러난다.

### 왜 신경망 추정기가 지는가 — 구조적 이유

측정값이 각 모델의 **bin 격자의 정확한 배수**로 나온다.

| 주입 | PESTO 측정 | CREPE 측정 |
|---|---|---|
| 7 cents | 0.0 = 33.33 × 0 | 0.8 = 20 × 0.04 |
| 23 cents | 33.3 = 33.33 × 1 | 19.8 = 20 × 0.99 |
| 47 cents | 66.4 = 33.33 × 2 | 39.9 = 20 × 1.99 |

PESTO 의 VQT 는 3 bins/semitone = **33.33 cents**, CREPE 는 **20 cents** 폭이다.
argmax-국소 가중평균으로 연속값을 내지만, **정상(定常) 음에서는 한 bin 에 고정**된다.
문헌도 "CREPE 의 양자화 오차 기댓값은 5 cents" 라고 적고 있고, 우리 측정 5.44 와 일치한다.

이건 하이퍼파라미터 문제가 아니라 **분류 기반 피치 추정의 구조적 한계**다.
반면 자기상관 + 포물선 보간(yin)은 격자가 없다.

### 다만 PESTO 는 변조에서 가장 좋았다

| 추정기 | 비브라토 40c | 80c | 120c |
|---|---|---|---|
| PESTO | **35.0** | 76.8 | **120.1** |
| yin | 38.8 | **76.0** | 114.9 |
| CREPE | 26.1 | 62.5 | 105.8 |
| SwiftF0 | 12.8 | 57.8 | 106.2 |

**정지된 음에서는 bin 에 갇히지만, 음이 움직이면 프레임마다 bin 을 넘나들며
변조를 복원한다.** 흥미로운 성질이고 논문에 적을 가치가 있다.
다만 yin 과 실질 동률이라 추가 backend 를 들일 이유는 없다.

## (C) 속도

| 추정기 | s/클립 | 20만 클립 (1코어) |
|---|---|---|
| yin | 0.003 | 0.2 h |
| SwiftF0 | 0.095 | 5.3 h |
| pyin (r=0.05) | 2.165 | 120 h |

## 결론

- **F0 값 = `yin`.** 차분 오차 0.29 cents, 2위의 8배 정확, 가장 빠름.
- **voiced 판정 = SwiftF0** (사전고정 backend). 유성음 판정은 격자와 무관하고 안정적이다.
- 두 backend 값을 같은 열에 섞지 않으며 행마다 backend 를 기록한다.

절대 음정은 여전히 주장하지 않는다(yin 은 음고마다 상수 편향이 있다).
모든 음정 결론은 **같은 음을 조건끼리 비교한 차이**로만 말한다.

10,368행 · prompt 24개 · **prompt 단위 GroupKFold 5겹** · 전부 기본 하이퍼파라미터.

| 모델 | MAE (dB) | R² | 학습+평가 |
|---|---|---|---|
| ExtraTrees (기존) | 1.836 | 0.693 | 9.0 s |
| CatBoost | 1.796 | 0.716 | 8.4 s |
| HistGradientBoosting | 1.784 | 0.721 | 59.7 s |
| **LightGBM (채택)** | **1.784** | **0.721** | **2.2 s** |

정확도 개선은 2.8% 로 크지 않다. **채택 이유는 4배 빠른 속도**다 —
능동학습 루프는 대리모델을 수십 번 재학습하므로 학습시간이 곧 탐색 횟수가 된다.
(표형 데이터에서 GBDT 가 딥러닝을 앞선다는 것이 2025년 기준 다수 벤치마크의 결론이다.
TabPFN 계열 foundation model 이 대안으로 부상 중이나 이 규모에서는 검증 필요.)

## 학습된 표현 축 (MERT) — 해석가능 특징의 감사

### 왜 넣는가

headline 지표는 전부 **우리가 고른 21개 해석가능 특징** 위에서 계산된다.
해석 가능한 건 장점이지만, 뒤집으면 **그 21개가 놓친 변화는 영원히 안 보인다**.
"누출이 없다"는 결론이 실제로는 "우리 특징으로는 안 보인다"일 수 있다.

MERT([arXiv 2306.00107](https://arxiv.org/abs/2306.00107))는 음악 오디오로 자기지도
학습된 표현이다. 무엇을 재야 할지 미리 정하지 않았으므로:

- **MERT 에서 차이가 보이는데 해석가능 특징에서 안 보이면** → 특징 설계의 구멍이 드러난다
- **둘 다 보이면** → 결론이 훨씬 튼튼해진다
- **둘 다 안 보이면** → "누출 없음" 이 진짜에 가까워진다

MERT 는 headline 지표를 **대체하지 않는다. 감사의 감사다.**

### 왜 C2ST 인가

임베딩은 768~3072 차원이라 energy distance 같은 거리 기반 통계량이 차원의 저주로
둔해진다. **분류기 이표본 검정(C2ST)** 은 분류기가 판별 방향을 스스로 찾으므로
그 영향을 덜 받고, 결과가 **정확도**라 해석이 바로 된다.

```
정확도 0.5 -> 모델의 강약 변화가 실연주의 변화와 구별되지 않는다  (좋음)
정확도 1.0 -> 완전히 다른 방식으로 변한다                        (제어가 실악기와 다르게 작동)
```

p 값은 이항검정으로 바로 나온다. 검증 테스트는
`tests/test_metrics_calibration.py::test_c2st_detects_difference_and_accepts_identical`.

### ⚠ MERT 는 음량을 보지 못한다 (실측)

| 비교 | 코사인 유사도 | 해석 |
|---|---|---|
| A4 vs A4 (반복) | 1.0000 | 결정적 (정상) |
| A4 vs E5 | 0.6053 | 음정 구별함 |
| A4 vs A4 밝게 | 0.9046 | 음색 구별함 |
| **A4 vs A4 −12 dB** | **1.0000** | **음량 구별 못함** |

`Wav2Vec2FeatureExtractor` 가 입력을 zero-mean/unit-variance 로 정규화하기 때문이다.

**이걸 모르고 쓰면 "MERT 로 봐도 다이내믹 누출이 없다" 는 거짓 결론이 나온다.**
MERT 는 애초에 음량을 볼 수 없다. 역할을 이렇게 나눈다:

- **음량(목표 축)** → 해석가능 RMS 특징. ±0.5 dB 로 검증됨.
- **음색·음정·아티큘레이션(누출 축)** → MERT 교차확인. 우리 특징이 놓쳤을 위험이 가장 큰 곳.

회귀 테스트: `tests/test_embeddings.py::test_mert_is_level_invariant_by_design`

### 레이어 선택

음악 SSL 모델은 **하위 레이어일수록 음향적(음색·피치), 상위일수록 의미적(장르·무드)**
이라는 것이 층별 분석 연구들의 일관된 보고다. 우리가 감사하는 건 연주 표현이므로
중하위 레이어(기본값 3–6)를 쓴다. 전 레이어 평균은 성격이 다른 층을 섞어 신호를 흐린다.

### ⚠ 환경 제약 (서버에서 반드시 확인)

MERT 저장소는 **safetensors 를 제공하지 않고** `pytorch_model.bin` 만 올려 두었다.
transformers 는 CVE-2025-32434 때문에 **torch < 2.6 에서 `torch.load` 를 거부**한다.

```
m-a-p/MERT-v1-95M   safetensors 없음 / pytorch_model.bin 만
m-a-p/MERT-v1-330M  safetensors 없음 / pytorch_model.bin 만
```

그래서 임베딩은 **별도 venv**(`.venv-embed`, torch>=2.6)에서 돌린다.
분석용 `.venv` 에 torch 를 넣지 않는다는 방침, VIOLET venv 의 torch 고정과 모두 충돌하기 때문이다.

```bash
bash scripts/setup_embeddings_env.sh   # 한 번
bash scripts/run_embeddings.sh expanded
```

`src/viocf/embeddings.py` 의 `_require_backend()` 가 torch 버전을 먼저 검사하고
못 미치면 이유를 적어 즉시 중단한다(서버에서 몇 시간 뒤 알 수 없는 오류로 죽는 것 방지).
